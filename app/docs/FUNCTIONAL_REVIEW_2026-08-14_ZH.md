# ChatMandarin 功能设计与实现深度评审（2026-08-14）

## 结论

项目已经具备“学习路径 → 场景对话 → 跟读/配音/HSKK → 错题复习 → 订阅”的完整产品骨架，但此前存在三类会直接损害用户信任的问题：评分标准由客户端回传、配额记录在 RLS 下无法可靠写入、部分页面展示了底层引擎并不具备的测评精度。本轮已修复可直接落地的 P0/P1 问题，并建立首批自动化回归测试。

## 已修复问题

| 优先级 | 问题 | 用户影响 | 修复 |
| --- | --- | --- | --- |
| P0 | HSKK 最后一段录音写入 state 后立即读取旧 state | 完成第三段后仍提示缺少录音，流程无法提交 | 提交函数显式接收刚录完的 Blob |
| P0 | `usage_stats`/`usage_monthly` 只有 SELECT RLS，应用又忽略写错误 | 免费配额可能永远不累计；并发请求还能超额 | 新增数据库原子配额 RPC，在事务内锁行、校验身份、检查并递增 |
| P0 | HSKK 一次请求先消费一次、成功后又手工加一次 | 免费用户完成一次就可能被记两次 | 删除重复计数，只保留原子消费 |

| P1 | 跟读“声调分”始终为 100（实现实际没有声调检测） | 向用户展示虚假的能力评价 | 不再生成声调分，UI 明确说明当前引擎不提供声学声调评估 |

## 仍需规划的产品改进

### 1. 建立可信的语音评价层

当前 ASR 主要提供转写，不等于发音测评。建议把输出分成两层：

- 可立即可信展示：文本完成度、词句偏差、ASR 可懂度、回答内容相关性。
- 只有接入声学评测后展示：声调、声母/韵母、停顿、节奏、情绪。

验收标准应包含真实音频标注集，按 HSK 等级至少覆盖安静、噪声、口音和短录音四类样本；不能只用 LLM 自评。

### 2. 让学习闭环由“分数”转向“下一步动作”

每次练习结果应明确生成 1–3 个可执行动作，例如“重练这两个声母”“明天复习这个句型”“进入下一单元”。Dashboard 应展示最近 7 天完成的具体能力目标，而不只展示次数和平均分。

### 3. 增加入门分级与目标管理

首次使用建议用 3–5 分钟完成目标、现有水平、每日时间和薄弱项设置，再据此生成首周路径。当前按手工 HSK 等级进入所有功能，对不清楚自己水平的用户认知成本偏高。

### 4. 补齐支付事件顺序保护

Creem 会重试 webhook，事件也可能乱序到达。现有 event ID 能挡住完全相同的重放，但不同事件乱序仍可能让旧的 active 覆盖新的 expired。下一步应保存 `created_at`，以订阅为粒度只应用不早于已处理时间的事件，并把“记录事件 + 更新权益”放进一个数据库事务。

### 5. 建立可观测的产品漏斗

建议至少记录：注册完成、首次麦克风成功、首次练习完成、首次看到反馈、D1/D7 回访、触达额度墙、发起 checkout、支付成功。事件只记录业务状态和耗时，不记录原始语音或敏感文本。没有这组漏斗，后续功能优先级会继续依赖主观判断。

## 发布门禁

1. 先应用 `010_atomic_usage_quotas.sql`，再发布依赖新 RPC 的应用代码；顺序不可反转。
2. 使用 Node 20.19+；仓库提供 `.nvmrc` 固定本地推荐版本。
3. 串行执行 `npm run test`、`npm run type-check`、`npm run lint`、`npm run build`、`npm run voice:type-check` 和 `npm run voice:dry-run`。
4. 用 free/plus/pro 三类测试账号并发提交 HSKK、跟读和对话，核对日/月额度与前端提示。
5. 在 Creem 测试模式重放 paid、scheduled_cancel、past_due、expired、refund、dispute，并检查权益最终态。

## 已知残余风险

- `sharp < 0.35.0` 的 2026 libvips 公告仍由 Next 15 间接引入；npm 给出的自动修复要求升级 Next 16。当前应用没有使用 Next Image 处理用户可控图片，实际暴露面较低，但在完成 Next 16/React 兼容回归前不能宣称依赖审计清零。
- API 路由测试目前覆盖纯业务规则，尚未建立带 Supabase/Creem/语音网关替身的端到端契约测试。
- 配额在通过输入校验、开始调用付费上游前被预留；上游失败仍计为一次尝试。若产品承诺“失败不扣额度”，需要增加可审计的补偿事务。
